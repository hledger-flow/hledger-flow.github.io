Choosing the tool

Section titled “Choosing the tool”

hledger-flow suggests the usual way forward: a preprocess script that turns the JSON into CSV, with one row per tip, and a rules file for the rest. For most JSON exports, that’s the right choice, because the rules still do the classifying.

But hledger’s rules turn each CSV row into its own transaction. Gawie wants one transaction per shift, holding all of that shift’s tips in their different currencies. That’s a transaction shape no rules file can build from separate rows.

When you need to write the transactions yourself, use a construct script. If an account directory has an executable called construct, hledger-flow runs it instead of using a rules file. It gets the statement’s path, a -, and the bank, account and owner names, and writes hledger journal entries to standard output. hledger-flow checks them with hledger and saves the result in 3-journal/.

hledger keeps each currency separate. To see the tips in rand, it needs exchange rates. hledger-flow includes prices/<year>/prices.journal in the ledger for that year, so Gawie saves the rates he looked up as prices/2016/prices.journal:

Which tool when

Section titled “Which tool when”
The statement… Use As in
is a CSV with a header row the rules file status --rules-template drafts Part 1
needs categories if blocks, shared with include Part 2
has extra rows, odd dates or split columns skip, if tables and rules functions Part 3
needs information from another row, or isn’t CSV a preprocess script that fixes only that, plus rules Part 4
needs transactions no rules file can build a construct script Part 5

Start at the top of the table, and move down only when the row above can’t do the job. The further down you go, the more of the conversion is code you maintain yourself.
